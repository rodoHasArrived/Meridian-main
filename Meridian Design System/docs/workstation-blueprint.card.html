Workstation blueprint v2.0

The production structure for Meridian workstation templates: repository conventions plus the Programmed Institutionalism rules — one dominant work plane, a paper–plate–well material hierarchy, explicit data states, traceable evidence, restrained brand expression.

Full text: docs/WORKSTATION_BLUEPRINT.md · Folder conventions + entry contract: templates/README.md · Component choice: guidelines/PATTERNS.md · Recipes: docs/COOKBOOK.md

Meridian should organize complexity before it decorates it.

01

Design contract

satisfy before component styling
  1. Choose one workspace archetype — never a generic dashboard grid.
  2. Establish one dominant work plane; secondary regions support it.
  3. Use the material hierarchy intentionally — Paper, Plate, Well, Rail, Overlay.
  4. One primary action per operational region, resolving to graphite or deep slate.
  5. Make data trustworthy at a glance — state, source, freshness, as-of.
  1. Separate brand from semantic color. Terracotta is not loss, error, or warning.
  2. Sentence case for working UI; uppercase for environment and compact indices.
  3. Reduce containers before reducing type — density from alignment, not 10px text.
  4. Primitives only when they carry meaning — Datum, Field, Trace, Plate, Capsule.
  5. Preserve operability — keyboard, 200% zoom, no color-only meaning.
02

Pick the archetype first

declare in screen comment + root class
ArchetypePrimary purposeDefault composition
MonitorScan status and detect changeSummary strip, dominant operational plane, narrow alert/freshness rail
AnalyzeManipulate assumptions, inspect patterns8-col analytical well, 4-col scenario plane, lower comparison band
InspectUnderstand one entity deeplyStable identity header, ordered detail sequence, persistent evidence region
CompareEvaluate standardized peersRepeated Plates sharing scale, label order, padding, annotation position
ReconcileResolve exceptions, confirm stateTable-first plane, queue/filters, selected-record evidence, explicit resolution
ComposeArrange research or workspace modulesStable application core with snapping, saveable Capsules

Rule. A rectangular panel is not automatically a Capsule. A Capsule is movable or replaceable, has a data contract, predictable controls, saved state, and standardized dimensions.

03

The shell is a component

WorkstationShell — never hand-rolled

One frame, five slots

<WorkstationShell
  archetype="reconcile"
  labelledBy="workspace-title"
  topbar={<WorkstationTopbar …/>}
  nav={<NavRail …/>}
  aside={<EvidenceRail …/>}
  statusBar={<StatusBar …/>}>
  {/* dominant work plane */}
</WorkstationShell>
  • The shell renders the <main> landmark and crash-isolates main + aside — a failing panel never blanks the chrome.
  • No hand-rolled flex scaffolding, no second <main>, no local 100vh or row-height override.
  • Scrolling lives in the shell's main region, never on the document body.
  • Folder anatomy and the seed-data load order: templates/README.md.

Slot order

WorkstationShell
├── topbar      WorkstationTopbar
├── nav         NavRail
├── children    dominant work plane
├── aside       evidence rail (optional)
└── statusBar   StatusBar

Workspace layers, in order

  1. Header — title, context, as-of, coverage, one primary action.
  2. Control band — tabs, saved views, search, filters, scenario inputs.
  3. Dominant work plane — table, chart, relationship view, composition surface.
  4. Evidence region — provenance, selected record, audit trace, alerts.

One h1 per screen, named to the shell via labelledBy; the Meridian mark appears once, in the chrome.

04

Surface hierarchy

semantic surfaces, not a universal card
SurfacePurpose & treatment
PaperApplication canvas — warm neutral, no border
PlateDominant/standardized region — continuous light plane, structure via spacing
WellTable, chart, matrix — near-white, minimal internal framing
RailNav, filters, queue, context — slightly darker neutral
OverlayModal, menu, drawer — elevated, restrained shadow
SignalRare branded moment — controlled terracotta, never a semantic state

Avoid

  • A grid of equally weighted bordered panels.
  • Default shadows on every region; a card inside a card.
  • Warm beige on every nested surface.
  • Terracotta borders around every active control.
  • The Meridian Field used as background texture.

Primitives

Datum · orientation & selection Field · every mark encodes data Trace · lineage & audit Plate · honest comparison Capsule · Compose only

Evidence rail for inspection that must stay visible; Dialog only for bounded create/edit and confirmations — never to show row detail. Width is size (sm 420 · md 520 · lg 720), not a second component.

  • No universal T-shirt scale: Button is sm|default|lg|icon; many controls are sm|md|lg. Check the .d.ts.
  • Scope every rule under the workstation root; centralize fallbacks in one alias block; never !important.
  • 1px rules for structure, 2px for focus and selected Datum rails.
  • Motion: 80 / 120 / 180 / 240 / 280ms — Reflow, Trace, Reconcile, Focus. No bounce or glow.
07

Quality gate

ready for review only when every answer is yes
  1. Is the workspace archetype explicit?
  2. Is there one clearly dominant work region?
  3. Does each surface have a defined Paper/Plate/Well/Rail/Overlay/Signal role?
  4. Are related regions combined before new borders are added?
  5. One primary action per operational region?
  6. Are brand and semantic colors separated?
  7. Do important values carry state, source, freshness, or as-of?
  8. Are zero, missing, no activity, and not applicable distinguishable?
  9. Do comparable objects share geometry and scale?
  10. Does selection use a persistent Datum, not a decorative accent border?
  11. Does every Field encode real information?
  12. Is selected-record evidence available without losing the workspace?
  13. Is the screen understandable without motion?
  14. Can the primary workflow be completed by keyboard?
  15. Is the layout intentional in dense/default host mode?
  16. Does the narrow layout become a focused task flow, not a card stack?
  17. Is it recognizably Meridian without repeated logos?
  18. Does it use only supported component props and variants?
  19. Is the frame WorkstationShell — no hand-rolled chrome, no second <main>?
