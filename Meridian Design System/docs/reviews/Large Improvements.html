4.1 proved the component work was not done. It also proved that reading source is not a method.

The 14 Aug brainstorm opened with "the component work is done." Two weeks later 4.1 has fixed calendar dates that were a day early for every operator west of Greenwich, a MultiSelect whose "Select all" called onClearSelection(), a DatePicker with no keyboard support at all, a Combobox that hardcoded one DOM id for every instance, and a SplitPane writing localStorage on every pointermove. Excellent work, and every item was found the same way: a person opened the file.

So the small items were never the risk — the discovery method is. Everything below is release-scale, and each one changes what the system can be wrong about rather than fixing one thing it is wrong about. Same bar as last time: every candidate starts from a fact in this repository, and each carries the argument against itself.

L-01Numbers need the authority that localDate.js just became for datesdo next
Evidence

Ten modules, one literal each BasisComparisonMatrix · RollforwardMatrix PostingImpactPreview · ScheduleLadder VarianceCell · TieOutPanel · CommitmentBar MaturityLadder · CashFlowLadder MaterialityAssessment → new Intl.NumberFormat("en-US", …) accounting/money.js takes locale — parameterized core/Timestamp takes locale — parameterized STATES_AND_ANTIPATTERNS ❌ "formatting data by hand"

The law already bans this by name — for dates and deltas. The accounting tier, which is the tier that formats money for a living, bypasses the one sanctioned helper and hardcodes a locale. (Count is from a single grep for Intl.*Format; bare toLocaleString callers are not in it, so ten is a floor.)

This is not only an i18n gap. 4.1 fixed decimals by hand twice — a stale bundle serving the old priceDecimals default, then trading-desk hardcoding 2dp in four places — because precision has no owner either.

The move

core/format.js as the single numeric authority, exactly as localDate.js is now the calendar-date authority: money, quantity, price-to-tick, percent, basis points, compact, signed delta, accounting negatives, thin separators — one implementation, locale and currency from context, decimals from the instrument rather than the call site.

Then a FormatProvider at the shell (locale · currency · numerals · negative style), per-surface override for the one table that must show source-currency, and the gate that makes it hold: a bare Intl. constructor outside core/format.js is a governance violation — the same shape of rule as "never route a calendar date through toISOString()," which is the only kind of rule this repo has found to stick.

Where it pays off beyond locale: FX revaluation, the ALM ladders and the basis matrices are the surfaces most likely to be read by a desk that writes 1.234.567,89, and they are precisely the ten files above.

Cost a release · authority is a sitting, the sweep and the gate are the work · Risk every number on every screen moves at once — do it with the harness in L-02, not before it

L-02A conformance harness over the 120 cards — the defect classes are all machine-detectabledo next
Evidence

4.1's own findings, as classes duplicate hardcoded DOM id Combobox no keyboard model at all DatePicker missing aria-setsize/posinset TreeView row height pinned, density ignored Stepper 11px · Tree 30px transition:all vs. the motion rule Stepper · MultiSelect inline styles, no tokens MultiSelect storage write per pointermove SplitPane missing type="button" in a form DatePicker _adherence.oxlintrc.json exists, generated, nothing in the repo runs it counts drifted again since 17 Aug: manifest 292 / 120 vs. docs 284 / 118

The move

Two gates, one scoreboard. Static: actually run the adherence ruleset the compiler already emits, extended with the classes above — literal ids, `transition:all`, hardcoded px row heights, inline-style components, bare `Intl.`, remote `@import`. Every one of those is a regex-grade rule, and each already has a shipped violation to test against.

Dynamic: assertion checks over the 120 specimen cards — every interactive card gets focus-order, accessible-name, role, `Escape`, and re-render-stability assertions. The cards exist; today they are looked at, not asserted against.

Scoreboard: a generated Documentation card and landing strip, so the conformance claim on the page is the last run — which also retires the count drift above, because the numbers stop being typed.

L-03An action contract, then bind one screen to a real transportdo next
Evidence

templates/ 27 screens · zero I/O (the only fetch in the tree is generated support.js loading the page's own source) DEPLOYMENT_CHECKLIST_4_1 asks, in prose, per action: endpoint · idempotency key · permission · optimistic-or-confirmed · failure surface → for 3 screens, answered by a human, once ADAPTER_SEMANTICS "a failed adapter makes an instruction unlanded" — stated for adapters, absent from every control that submits one trading-desk autoFill tweak: orders rest or fill because a timer says so

The move

Give the submitting side the vocabulary the reading side has. One primitive — call it an action envelope — where a mutating control declares its idempotency key, its permission, whether it is optimistic or confirmed, and what its failure surface is; and renders the four states the checklist implies: in flight · landed · unlanded · rejected-with-reason. ActionGuard answers may I; nothing answers did it.

Then prove it: bind trading-desk's order path and ingestion-operations' job queue to a local mock transport with latency, duplicate submits and a 500 — so the states are exercised rather than asserted, and a double-clicked Submit is a test rather than an incident.

Argument against: a design system that ships a transport is over-reaching, and the fixtures are what make the templates copyable. Answer: the contract is the deliverable; the mock lives in tests/, not in the templates, and every screen keeps its fixture.

Cost a release · Payoff makes the deployment checklist mechanical instead of a promise · Call is there a real API to bind against, or is the mock the ceiling?

L-04The archetype should own its collapse order — and the dock grips should stop lyingneeds your call
Evidence

TEMPLATE_CONTRACT states a narrow-viewport rule reconciliation the only screen that implements it — local helmet CSS at ≤1180px + its own switch ScreenComposition declares regions, not their collapse order Capsule movable → ⠿ grip, no handler resizable → ⌟, no handler since 3.2 WorkspaceLayout (4.1) persists arrangement — the half that was missing is now shipped

The move

4.1 changed the economics here: named, persisted, resizable screen arrangements now exist. What is still per-screen improvisation is the automatic half — which region folds first, into what, at what width. Regions already declare priority in an archetype; let ARCHETYPES declare collapse order and let one switch component execute it, so twenty-six screens do not write it twenty-six ways.

Same release, two lines of deletion: Capsule's movable/resizable have advertised a capability for three releases on the exact surface (an ops wall) where operators expect it. Either point them at WorkspaceLayout or delete the props — an affordance that renders a grip and does nothing is worse than no affordance.

L-05Subtract — and put a deletion budget in the release protocolneeds your call
Evidence

101 of 284 exports used by no screen 79 live only in a specimen card 4.0 curated templates 32 → 26 4.1 added exports again (layout · trail · handover · adapters · disclosure) net screens down, surface up

I-09 left this as "your call" and it stayed uncalled while the surface grew another release. Meanwhile NotificationCenter sits card-only while alerting-workstation hand-rolls its own triage rail.

The move

The generated tier from I-09 — demonstrated · offered · candidate — is table stakes and cheap. The large version is a rule: a minor release may not increase net public exports. New capability arrives with either an adopting screen or a retirement, in the same release.

Argument against, and it is real: a card-only chart costs nothing at runtime — it is in the same monolithic bundle either way — so the cost is documentation and maintenance, not bytes. Measure that: exports touched by a fix in the last three releases, not exports counted. If the tail never changes, the tail is not what is expensive.

Cheaper alternative to deletion, same effect: build the one screen that promotes four card-only charts at once (an exposure/attribution surface takes Treemap, WaterfallChart, BarChart, ComparisonPlate). Then the tail is a decision, not an accident.

L-06Twelve normative documents, no index — number the lawthe release after
Evidence

guidelines/ 30 files · docs/ 25 · Documentation cards 20 Normative, all of them: OPERATING_LANGUAGE · TIME_SEMANTICS VISUALIZATION_GRAMMAR · PROGRESSIVE_DISCLOSURE SESSION_CONTINUITY · ADAPTER_SEMANTICS DECISION_SEMANTICS · VALUE_ENVELOPE TABULAR_CONTRACT · STATES_AND_ANTIPATTERNS TEMPLATE_CONTRACT · WORKSTATION_HIERARCHY A component author must know which of the twelve bind them → no index says

The move

Not a rewrite — an index and a citation contract. Each normative statement gets an id (R-nn); each <Name>.prompt.md cites the rule ids it satisfies; the governance script checks that every component cites at least the rules its domain makes mandatory, and that every rule is cited by something. A rule nothing cites is either dead law or an unadopted capability, and today there is no way to tell which.

The test of whether this earned its place: a component review can be conducted by rule id, and a new author asks "which rules bind a chart?" and gets a list instead of twelve documents.

Argument against: this is the candidate most likely to become bureaucracy. Mitigation — ids only for statements that are already imperative in the prose. If a guideline yields no imperatives, that is the finding.

Cost half a release, mostly reading · Payoff the review of every future component gets shorter

L-07A stated support window and a generated deprecation ledgerthe release after
Evidence

codemod_4_0.py one release, one script 4.1 shipped an intentional break (MultiSelect, SelectCheckbox removed) VarianceCell.tolerance deprecated, not removed --accent "deprecated alias through 3.x" Nowhere how long a deprecation survives

The move

State the window (deprecate in a minor, remove in the next major, never inside a patch) and generate the ledger from source: export → deprecated in → removed in → codemod entry → replacement. A consumer on 3.x should be able to read one table and know what their upgrade costs.

Small file, structural effect: it is the difference between a system that breaks consumers politely and one that breaks them unpredictably. It also makes L-05's deletions possible — right now there is no sanctioned way to remove anything.

needs two answers from you first

The one-line version. The system's reading vocabulary is world-class and its writing vocabulary barely exists (L-03); its law is enforced by careful people rather than by builds (L-02, L-01); and it grows faster than it is adopted (L-05). Those are the three large things. Everything else on this page is downstream of one of them.
Open question 1 — is there a real API to bind a screen against, or is a mock the ceiling? L-03's contract is worth writing either way; what changes is whether 4.3 ends with a screen talking to Meridian, or a screen talking to a fixture that lies convincingly.
Open question 2 — are operators ever on a narrow viewport? (asked 14 Aug, still open) "No, it is a 27″ desk or two" collapses L-04 from a release to a two-line deletion. Nothing else in the backlog is this sensitive to one answer.
Open question 3 — fewer components, or more screens? L-05 needs a direction, not a number. More screens is the answer I would pick — a screen is the only thing that has ever promoted an export out of the tail — but it costs a release per screen, and it grows the surface it is meant to justify.
