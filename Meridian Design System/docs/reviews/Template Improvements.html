MERIDIAN DESIGN SYSTEMTEMPLATE IMPROVEMENTS · 2026-08-06

Proposal · templates/ · 28 folders · implemented 2026-08-06

The templates are good screens and weak templates.

Each folder renders a credible workstation. As templates — things a consumer copies, opens, and edits — they under-deliver in four repeatable ways: the markup is unreachable to the editor, the scaffolding has forked into five incompatible copies, the contract the README advertises is met by a minority of folders, and the set has grown overlapping surfaces nobody pruned.

Nothing below asks for new visual design. It is consolidation, contract enforcement, and one structural change to how a template is authored. Graded on the system's own ladder: Blocked = a consumer is actively misled; Action = duplicated or dead weight; Review = a judgement call worth making on purpose.

T-01The template markup lives where the editor cannot reach itResolved · 2.1.0
Evidence
26 of 29 .dc.html entries are 19–20 lines: one <helmet> + one <x-import>. All screen markup sits in screen.jsx. README: "the entry … Directly editable in the browser." False for 26/29.

A JSX subtree mounted through x-import is opaque to direct manipulation: a consumer cannot click a heading and retype it, cannot delete a panel, cannot drag-reorder cards. They must open a JSX file and hand-edit React — the exact work a template exists to avoid.

Proposal

Invert the ratio. The screen's own layout — masthead copy, section headings, panel titles, table column labels, empty-state prose, the arrangement of panels — moves into the DC template as static markup. screen.jsx shrinks to what genuinely needs React: interactive tables, charts, dialogs, live state, each mounted as a small named x-import.

Do it once properly on dashboard-workstation (the declared reference), publish it as the pattern, then convert in order of use. asset-sheet, report-pack and investment-event-ledger already work this way — they are the proof, not the exceptions.

Resolved in 2.1.0. All 28 entries now carry their screen content as directly editable markup; every screen.jsx monolith is deleted. The one helper that remains React is security-master-registry/registry-table.jsx — the column-managed data table, which is genuinely interactive.

T-02"Every template composes its frame from WorkstationShell" — four doBlocked
Evidence
WorkstationShell: 4 / 29 blank · dashboard · alerting · journaling <h1> landmark absent: 2 analytical-workbench · investment-event-ledger Env badge (Live/Paper/Fixture): 7 / 29 README contract claims all three, "enforced by scripts/check_design_system_governance.py". It is not.

Twenty-five folders hand-roll their own frame. Every one is a slightly different chrome a consumer may copy and propagate, and the <main> landmark the contract depends on comes from the shell.

Proposal

Pick one and mean it. Either (a) migrate all 29 onto WorkstationShell and let the governance script fail the build when a template does not use it, or (b) admit the shell is optional, rewrite the contract to require only viewport + <main> + <h1> + env badge, and enforce that.

(a) is the right answer — a shared shell is the reason a 29-template set looks like one product. Either way the governance script must actually assert the four rules; a contract nobody checks is a comment.

Action — forked scaffolding and duplicated weight02 / 04

Mechanical, low-risk, and each one currently costs every future template a decision it should not have to make.

T-03Five ds-base.js variants and five runtime versionsAction
Evidence
ds-base.js — 5 distinct files: 13 tmpl · styles.css only 12 tmpl · 10 stylesheets incl. dark + print 2 tmpl · 6 stylesheets, no dark, no print 1 tmpl · 8 stylesheets 1 tmpl · truncated error message support.js — 5 versions, 53,959 → 69,134 bytes oldest: accounting · split-pane (15 kB behind)

Consequence: whether a copied template supports dark mode or prints correctly is decided by which folder the consumer happened to copy. Templates on the 53 kB runtime are two generations behind on DC behaviour.

Proposal

One canonical ds-base.js, loading the full token set (dark and print included), written to all 29 folders by a script — scripts/sync_template_scaffold.py — that also refreshes support.js to the current runtime and fails CI when any folder drifts.

Scaffolding is generated, not authored. Nobody should be reviewing a diff of a loader file again.

T-04Three reconciliation surfaces; five strategy surfacesAction
Evidence
Reconciliation appears as: reconciliation-workstation/ 15 kB split-pane-reconciliation/ 36 kB accounting-workstation/views/ReconciliationView Strategy appears as: builder · onboarding · runs · backtest-builder · backtest-compare

A consumer choosing between them has no basis for the choice — the picker shows 29 flat entries and three plausible reconciliation names.

Proposal

Merge the two reconciliation templates into one (reconciliation-workstation, keeping the split-pane matcher as its dominant work plane); the accounting view stays, as a tab inside a larger workstation, which is a different job.

Keep all five strategy templates — they are genuinely distinct steps — but say so in their descriptions: "step 1 of the strategy flow", "compare two completed runs". Net: 29 → 28 folders, zero ambiguity.

T-05Missing preview sizes, missing tweaks, off-convention namesAction
Evidence
$preview declared: 2 / 29 editor tweaks declared: 5 / 29 (3–6 props each) Filename off-convention: Split Pane Reconciliation.dc.html (spaces; rule is PascalCase) Stray index.html in: charting · dashboard · security-master-registry
Proposal

Every template declares $preview at its true working size (1920×1080 for workstations, 1440×900 for sheets, Letter for report-pack) so the picker thumbnails stop guessing.

Every template declares 2–3 tweaks that in-place editing cannot do: density (terminal/compact/spacious), theme (light/dark), environment (Live/Paper/Fixture). Those three exist as real token scopes and would demo the system's best feature on every screen. Rename the one off-convention file; delete or justify the three stray index.htmls.

T-06Templates ship the happy path onlyReview
Evidence
EmptyState used: 6 / 29 Skeleton* used: 2 / 29 error / degraded state: 3 / 29 @media query anywhere in templates: 0 Blueprint doc specifies a "full data-state ladder".

alerting-workstation is the only folder that demonstrates the ladder end to end. Copy any other template and the loading, empty, and failed states are the consumer's problem — the states that are hardest to design and most often skipped.

Proposal

Require the ladder in the contract: every template renders loading → empty → populated → error for its dominant work plane, switchable from a dataState tweak. It costs roughly 20 lines per template and makes the set worth copying for reasons beyond layout.

On width: workstations are desktop instruments and 0 media queries may be correct — but decide it, write it into the blueprint as a stated non-goal, and stop leaving it implicit.

T-0729 flat entries in the pickerReview
Evidence

Templates surface as one undifferentiated "Templates" group. The blueprint already defines workspace archetypes — monitor, reconcile, and the rest — and templates pass one to WorkstationShell, but that classification is invisible at the point of choosing.

Proposal

Group by archetype in the name field until the picker supports groups: Monitor (dashboard, trading desk, alerting, ingestion, strategy runs), Investigate (reconciliation, security master, analytical workbench, backtest compare), Compose (strategy builder, basket builder, field & formula, journaling), Report (report pack, library, scheduler, asset sheet), Admin (settings, session start, governance, onboarding).

Also front-load the descriptions: several run past 160 characters and are truncated exactly where the distinguishing detail sits.

Proposed order of work04 / 04

Sequenced so the mechanical wins land first and the structural change happens once, on the reference template, before it is repeated 28 times.
