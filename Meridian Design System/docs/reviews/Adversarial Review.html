MERIDIAN DESIGN SYSTEMADVERSARIAL REVIEW · 2026-08-06

Internal audit · disposable artifact

The system is strong. Its edges are not.

193 exports, 29 templates, 91 cards, 622 tokens, and a governance checker that passes clean. The core is genuinely well-built — the token tiering, the data-condition vocabulary, and the per-component .prompt.md discipline are better than most shipped systems. This review ignores all of that and attacks only what is weak: material that no longer earns its place, and implementations that contradict the system's own law.

Findings are graded with the system's own severity ladder. Blocked = the system contradicts itself and will mislead a consumer. Action = dead or duplicated weight. Review = a judgement call worth making deliberately.

Self-contradiction — the system disobeys itself01 / 04

These are the expensive findings. A design system's only real asset is that its documentation can be trusted; each of these teaches a consumer to do the wrong thing.

C-01The flagship shell component is used by nothingBlocked

Evidence

readme.md › shell/ "WorkstationShell (slot-based frame — chrome slots around a crash-isolated main + optional right rail; use instead of hand-rolled flex scaffolding)" grep WorkstationShell templates/ → 0 matches / 29 templates

Every template instead hand-rolls <main style={{flex:1, overflowY:"auto", padding:16 …}}> — and guidelines/WORKSTATION_BLUEPRINT.md §3 teaches that hand-rolled version as the standard, directly contradicting the readme.

Why it matters & what to do

An abstraction with zero internal adoption is an untested abstraction. Its crash-isolation and right-rail slots have never run in a real screen, so the first consumer to follow the readme is the integration test.

Decide one way. Either migrate 3–4 templates onto WorkstationShell (starting with blank-workstation, whose whole job is to be the reference shell) and make the blueprint teach it — or delete the component and stop advertising it. Half-shipped is the only unacceptable state.

C-02Row height has three different official answersBlocked

Evidence

readme.md terminal 26 · dense 28 · standard 36 · review 44 DenseDataTable.jsx:101 "32 compact · 40 cozy · 48 spacious" DenseDataTable.jsx:34 height: var(--theme-row-height, 40px) WORKSTATION_BLUEPRINT "40px default, 32px in FilteredDataTable"

The density scope names were renamed to terminal / dense / standard / review; cozy no longer exists anywhere in tokens/. The CSS fallback still resolves to the retired 40px.

Why it matters & what to do

The fallback is what renders whenever a consumer loads the bundle without styles.css — so the documented-wrong value is also the actually-wrong pixel. Three sources disagreeing means nobody has a way to be right.

Update the fallback to 36px, rewrite the prop comment to the current four scope names, and delete the size table from the blueprint (see D-05) rather than maintaining a fourth copy of it.

D-01Modal and Dialog are the same component with different prop namesAction

Evidence

Modal → open · onClose · closeOnEsc + Header/Body/Footer/Form Dialog → open · onClose · closeOnEsc + Header/Body/Footer (+ title, maxWidth, showClose) Both share core/useOverlayFocus.js. 9 of 193 exports. PATTERNS.md splits them by size: "confirm → Dialog (small, centered)" "form takeover → Modal (wider)"

A size distinction is a prop, not a component. And journaling-workstation — the only template using Modal — skips ModalHeader/ModalBody entirely and hand-writes .journ-modal-hd / .journ-modal-body CSS, so the compound API isn't earning its four extra exports either.

Why it matters & what to do

Nine exports, two .d.ts, two .prompt.md, a card, a lint rule, and a keyboard-map row that has to say “Dialog / Drawer / Modal” every time — all to express one overlay at two widths.

Keep Dialog (richer API, the one 3 templates actually chose), add size="sm|md|lg", port ModalForm to DialogForm, and alias Modal → Dialog for one release. Then migrate journaling-workstation and delete the hand-rolled modal CSS with it.

D-02Three components render a bar with a number on itReview

Evidence

ProgressBar value · max · label · size LinearGauge value · max · label · showValue · color · height Gauge value · max · label · size · color · thickness — radial SVG arc Template usage: Gauge 0 · LinearGauge 0

Why it matters & what to do

LinearGauge is ProgressBar with height instead of size. Merge it in.

Gauge is the sharper problem: a radial dial is the canonical dashboard-decoration trope, and this system's thesis is “no gradients, no glow, fine 1px rules, every pixel communicates information.” A 120px SVG arc to encode one scalar is the least information-dense option available, and nothing in the system uses it. Delete it — or, if a bounded-ratio display is genuinely needed, express it as a LinearGauge variant with a target datum, which matches the visualization grammar already written for IntervalBar.

D-03Three components are exported but invisible to the system's own censusAction

Evidence

On window.MeridianDesignSystem_205d17, but with no .d.ts and no .prompt.md: DockGrid 18,066 B 375 lines GroupedDataTable 13,300 B 269 lines ApprovalRequest 16,941 B 277 lines (+ ApprovalsInbox) Template usage: 0. Card coverage: 0.

Missing the .d.ts means the compiler never registers them as components — so the governance gate that enforces “*.prompt.md coverage for every component trio” never sees them, and passes clean.

Why it matters & what to do

48 KB of real, non-trivial code that a consumer can call, that no type checker describes, no lint rule constrains, no card demonstrates, and no gate protects. Worse: the gate reports success, so the gap is invisible.

Pick per component — promote (add .d.ts + .prompt.md + a card) or delete. My read: GroupedDataTable earns promotion (it fills a real hole beside Expandable/Filtered); DockGrid and ApprovalRequest look like speculative work with no home in any of the 29 templates.

Then close the hole: make the checker fail on a .jsx that exports a capitalized symbol with no sibling .d.ts.

Why it matters & what to do

“New” is a timestamp, not a category — and these cards are two releases old. A designer browsing the Core group sees “New Components” and “New Primitives” and has no way to know what's inside without opening both.

Rename by content (the subtitles already say it: Combobox · TreeView · Accordion · Callout · VirtualizedList), or fold them into the existing core.card.html / data.card.html galleries. Same for the two tests/ files — a “QA pass” for a specific review session is a dated artifact, not a standing suite.

D-05Four documents teach how to compose a screenAction

Evidence

guidelines/PATTERNS.md "composition & decision trees" docs/COOKBOOK.md "recipes → finished screens" templates/README.md "template anatomy" guidelines/WORKSTATION_BLUEPRINT.md "how a workstation screen is composed"

The blueprint is the weakest of the four and the most quotable. It teaches the hand-rolled shell (C-01), a stale size table (C-02), and closes with “Typical time: 30 minutes from scaffold to working prototype.”

Why it matters & what to do

Its own §"Size & scale reference" hardcodes eight pixel values in a system whose STATES_AND_ANTIPATTERNS.md says, of exactly this habit: “z-index: 9999 — don't; a magic number will collide.” The blueprint is the anti-pattern document's counter-example, shipped as law.

Delete it. Its two genuinely useful passages — the folder-structure diagram and the seed-data ordering warning about sibling *-data.js files — belong in templates/README.md, which is where someone copying a template actually looks. Marketing timings belong nowhere.

D-06An abandoned documentation pattern, 2/193 completeInfo

Evidence

components/core/Button.stories.html → group="Documentation" components/core/Input.stories.html → group="Documentation" …and 191 exports with no .stories.html. Meanwhile docs/COMPONENT_API_REFERENCE.card.html already renders the full prop table for every component.

Why it matters & what to do

Two components have a per-component API page; everything else doesn't. In the Documentation group they read as “Button and Input are documented, the rest aren't” — which is false, and unflattering.

Delete both, or drop the @dsCard tag so they stay as local scratch without claiming a slot in the tab. The API reference card is the pattern that scaled; back it.

D-07ui_kits/ is documented as a liabilityReview

Evidence

ui_kits/README.md: "…not the recommended starting point for new work: copy from ../templates/ instead, which stays current…" "When a product surface changes upstream, update the matching kit here so designers can diff intended vs shipped." 4 kits · ~57 KB · last touched before the v2.1 retone.

Why it matters & what to do

Four screens (dashboard, plottool, accounting, security-master) that each duplicate a template's job, that the README tells you not to use, and whose stated value — diffing intended vs. shipped — depends on a manual upstream-sync ritual with no owner and no gate.

Ask the honest question: has anyone run that diff? If not, delete the folder; the four templates cover the same surfaces and are held to the entry contract. If yes, it needs a sync date in github.md and a governance check, not a warning label.

D-08!important in four component stylesheetsInfo

Evidence

TrialBalance.jsx:33,36 .tbl__sec / .tbl__sub td backgrounds LedgerTable.jsx:41 .ldg__row--void td span color CorrelationHeatmap.jsx:20 .mds-corr__cell--diag background

Why it matters & what to do

Each is fighting the same thing: a row-level background set by a sibling rule at equal specificity. That's a cascade-ordering problem, not a priority problem — and every !important in a shipped component is a wall a consumer's legitimate override will later hit.

Low urgency, but fix by ordering (state modifiers after base rows) or one extra class on the selector. Then add !important to the governance checker's forbidden list so the count can't grow.

What survived the attack04 / 04

Named so the cuts above don't read as a verdict on the whole system. These are load-bearing and should not be touched in the cleanup.

The three-tier token model
Primitive → semantic → domain, with Tier 3 derived via color-mix() and never hardcoded. The white-label story actually works because of it.
Per-component .prompt.md
~140 of them, and the samples are substantive — behavior, state ownership, a usage example. Rare discipline. Keep the gate that enforces it.
The data-condition vocabulary
Ten conditions, text plus marker, and an explicit rule that a blank cell never encodes one. This is the system's best original idea.
Series roles over per-chart color
Color assigned by what a series is, not which chart it's in — and scenario deliberately separated from loss. Most systems never get here.
One signal, separate interaction family
Terracotta reserved for brand/scenario; blue for focus and selection. Prevents the classic bug where system feedback impersonates the brand.
Tables that prove their arithmetic
Imbalance flags, “Out by…”, gated posting, cent-exact allocation through shared money.js. The accounting domain is the strongest part of the system.
