# Accounting Configuration

**Owner:** Accounting / Fund Operations
**Scope:** Local workstation API, configuration DTOs, rule dry-run behavior, manual journal lifecycle actions, and audit evidence
**Status:** Shared browser/WPF accounting configuration and lifecycle foundation

---

## Purpose

Accounting configuration lets operators prepare ledger books, chart-of-accounts nodes, journal entry templates, posting rules, validation state, and configuration audit evidence before accounting rules are activated. The rule model now supports effective-dated, scoped, condition-driven posting rules with grouped `All`/`Any` predicates, formulas, weighted allocation expansion, deterministic priority validation, generated posting lines, dry-run previews, service-owned version history, and promotion-approval metadata. Allocation rows can use static weights or formula-backed weights during dry-run generation. Generated posting lines inherit rule scope, source-event dimensions, counterparty, line dimensions, allocation target dimensions, and external GL dimension keys before preview, so dimensional accounting context is retained through rule generation. Dry-run scope matching also enforces external GL dimension key/value pairs, so rules scoped to a GL department, class, book, or other external dimension do not match events from a different external dimension. Generated posting, chart paths, condition identities, amount-threshold predicate operands, allocation identities and formula references, effective-date windows, event-specific dry-run allocation weights, and ambiguous top-priority dry-run matches are validated fail-closed: duplicate formula ids, duplicate active chart account paths, missing generated-line formulas, missing or duplicate generated posting line ids, missing or archived generated posting account references, missing or duplicate allocation ids, missing or duplicate condition ids, malformed amount predicate values, inverted amount-between ranges, missing allocation formulas, formula weights that resolve non-positive in a dry run, impossible effective windows, and multiple matched rules sharing the selected top priority create critical validation issues and block activation or preview readiness.

This slice is internal-grade. Regulatory and allocator outputs remain filing-preparation or report-preparation artifacts unless a future external certification layer explicitly upgrades the output contract.

## Audit Coverage

Configuration mutations route through `IAccountingActionAuditStore`.

Each audit event records:

- Actor resolved from the authenticated workstation context.
- Action name.
- Fund profile and optional ledger book.
- Correlation id.
- Before and after configuration hashes.
- Validation issues observed after the mutation.
- Evidence links supplied by the caller.

Template preview, rule dry-run, and rule test-case execution do not append audit events and do not persist journal entries. Posting remains owned by existing ledger posting services.

Configuration activation now includes retained activation evidence and promotion-readiness gates. The activation request must carry retained activation, approval, certification, sign-off, or review evidence before `configuration.activate` can be audited. Active posting rules marked `RequiresPromotionApproval` must retain an approved promotion with approver, approval time, and retained approval, certification, sign-off, or review evidence links that identify the retained rule, current version, or approval id. Posting-rule upsert also retains a service-owned version row when a rule is created or its `RuleVersion` changes; that row captures actor, timestamp, evidence links, and the current promotion approval snapshot. The dedicated promotion-approval route approves only the current retained rule version, rejects stale-version approvals, requires approver notes plus retained rule/version/approval-specific approval/review evidence, requires retained saved regression coverage for that current rule version, runs those saved tests through the same dry-run assertion engine, updates the matching version snapshot, and appends `posting-rule.promotion-approve` audit evidence only after the current-version tests pass. If a materially changed rule carries forward the same approval id, the service clears the stale approval and returns the shared `posting-rule.promotion-approval-required` blocker until a fresh promotion approval is attached. Promotion-gated rules also need saved regression test coverage for the current rule version, saved rule test cases require retained regression/test/approval/certification/sign-off/review evidence that identifies the test case, expected rule, or expected version, and any saved rule test case that fails the shared dry-run assertion engine blocks activation.

Manual journal lifecycle actions append audit events for approval, posting, close-lock, and generated correction drafts. Human action origin is required for lifecycle transitions; assistant or automation-origin requests may draft support but cannot approve, post, reverse, rebook, or lock entries. Draft save and approval submission are accepted only for `Draft`, `NeedsFix`, or `Rejected` entries; submitted, approved, posted, reversed, rebooked, and close-locked entries must move through lifecycle actions or correction workflows and cannot be resubmitted directly. Approval and rejection actions require reviewer notes before the submitted entry transitions; posting and close-lock actions require operator notes before the approved or posted entry transitions. Close-lock actions also require retained close, period-lock, sign-off, certification, approval, or review evidence that identifies the journal entry or accounting period before the posted entry is frozen. Reversal and rebook actions require retained reversal, rebook, correction, approval, or review evidence that identifies the posted journal entry or accounting period before the posted entry is transitioned or a correction draft is generated; direct reversal/rebook is blocked once the entry is close-locked, so post-close correction flows must use late-adjustment or restatement governance. The service validates the generated correction draft before mutating the posted source entry, so invalid custom rebook lines cannot mark the original entry `Rebooked` while retaining a broken correction. The transitioned original entry and the generated correction draft both carry typed reversal/rebook link objects, and the correction draft carries its own generated-draft lifecycle transition so clients can render correction provenance without parsing memo text or audit action names. Requests can also carry period-lock posture; locked periods reject save, submit, evidence attachment, approval, posting, rejection, reversal, and rebook mutations, while validation remains non-posting and returns a critical `manual-je.period-locked` issue.

Manual journal normalization now treats `LedgerDimensionSetDto` as the canonical dimensional accounting envelope. Header dimensions are trimmed and retained with deterministic external-GL dimension keys; line dimensions inherit fund/entity and external GL scope from the header, while line-specific entity, instrument/security, tax-lot, and cost-center values override or enrich that scope. Save can retain incomplete drafts with dimension warnings, but approval validation requires fund and entity dimensions on the header and each normalized line.

## Durable Storage

When ledger Postgres storage is configured, `V_ledger_010__accounting_configuration.sql` creates:

| Table | Purpose |
| --- | --- |
| `accounting_configuration_workspaces` | Active workspace header, status, version, optional ledger book, and validation snapshot. |
| `accounting_configuration_chart_nodes` | Fund-scoped hierarchical chart-of-accounts nodes. |
| `accounting_configuration_journal_templates` | Fund-scoped journal template headers and JSONB template lines. |
| `accounting_configuration_posting_rules` | Fund-scoped source-event to template mappings. |
| `accounting_action_audit_events` | Append-only action audit events across configuration mutations and future accounting actions. |

`V_ledger_011__accounting_rule_payload.sql` adds `rule_payload` JSONB to `accounting_configuration_posting_rules` so effective-dated rules, conditions, formulas, allocation metadata, scopes, generated postings, versions, and promotion approvals survive durable PostgreSQL round trips while legacy columns remain queryable.

`PostgresAccountingConfigurationStore` implements `IAccountingConfigurationStore` and `IAccountingActionAuditStore`. The implementation uses the existing ledger schema options and keeps audit events append-only.

When Financial Operations is composed with `StorageOptions`, close late-adjustment review requests are retained at `accounting/close-management-late-adjustments.json` and accounting report package history is retained at `accounting/accounting-report-packages.json` under the configured storage root. These snapshots are written through `AtomicFileWriter` and are reprojected by the shared close-management and report-package endpoints after process restart.

## Browser Workflow

The browser workstation adds `/accounting/configure` as the Accounting Configure workstream.

The screen view model owns visible copy for setup status, validation issues, disabled preview reasons, template summary rows, preview status, and audit labels. React components render that view model and do not fork accounting validation or posting logic.

The same workstream now renders an Accounting Rules Studio over `PostingRuleDto`, `RuleDryRunResultDto`, saved rule-test cases, and rule-test suite DTOs. Operators can inspect effective dates, priority, dimensional scope, event predicates, grouped `All`/`Any` condition sets, formulas, allocation rows, generated posting metadata, retained versions, promotion-approval state, persisted regression assertions, and a selected-rule promotion readiness checklist covering version history, approval evidence, saved regression coverage, latest suite result, generated posting lines, dimensional scope coverage, and the activation gate, then duplicate the selected posting rule into a promotion-gated draft through `/api/ledger/accounting-configuration/posting-rules`, apply the selected dry-run source event as a required event-kind predicate through the same upsert route, apply the selected dry-run amount as a required `AmountGreaterThanOrEqual` predicate, apply the selected dry-run date as the retained effective start date, capture dry-run generated posting lines onto the selected rule as retained multi-line posting metadata, apply a dry-run generated posting amount onto the matching retained formula, apply deterministic generated posting dimensions onto retained allocation targets, apply unambiguous generated posting dimensions back onto the retained rule scope, raise the selected rule priority, archive an obsolete selected rule through the audited upsert route, run a non-posting dry-run preview through `/api/ledger/accounting-configuration/posting-rules/dry-run`, save the selected dry-run as a retained regression case through `/api/ledger/accounting-configuration/posting-rules/test-cases`, run a non-posting regression suite through `/api/ledger/accounting-configuration/posting-rules/tests`, or approve the current selected rule version through `/api/ledger/accounting-configuration/posting-rules/promotion-approvals`. Draft duplication clears carried promotion approval state, increments priority for review, retains browser evidence links, and selects the returned service-owned draft rule instead of fabricating client-local rule state. Event-predicate application replaces stale event-kind predicates, bumps the rule version, clears stale promotion approval, and requires fresh promotion before activation. Threshold application updates the retained condition set, bumps the rule version, clears stale promotion approval, and requires fresh promotion before activation. Effective-start application updates the retained effective window from dry-run evidence, clears stale approval, and keeps impossible windows from being introduced by clearing a stale end date that predates the new start. Generated-posting capture persists the service-produced posting-line metadata from the dry run, bumps the rule version, clears stale approval, and requires fresh promotion before activation so legacy template-derived previews can become first-class generated posting rules. Formula calibration persists the dry-run generated amount and currency onto the matching formula id, bumps the rule version, clears stale approval, and requires fresh promotion before activation. Allocation-target application merges deterministic generated posting dimensions onto formula-linked allocation target dimensions, bumps the rule version, clears stale approval, and requires fresh promotion before activation. Scope application promotes only single-value generated posting dimensions such as fund, entity, instrument, tax lot, cost center, counterparty, and external GL keys onto the retained rule scope, leaves ambiguous generated-line dimensions on the line metadata, bumps the rule version, clears stale approval, and requires fresh promotion before activation. Priority adjustment increments retained rule priority, bumps the rule version, clears stale approval, and requires fresh promotion before activation. Rule archiving marks the retained posting rule inactive through the shared configuration service, preserves history, clears stale dry-run preview state, and selects the next active rule returned by the workspace. The browser sends source-event, amount, currency, effective date, counterparty, dimension scope, generated posting lines, formula calibration, allocation target calibration, priority changes, and retained browser evidence for saved cases, event-predicate/effective-start/threshold/formula/allocation/scope/priority/draft/archival/generated-posting upserts, and promotion approval, but service-owned storage and audit determine the canonical workspace case set and approval state. Rule selection, generated balanced lines, merged dimensional envelopes, assertion issues, validation issues, explanations, and promotion approval mutation remain service-owned; an exact retry of an already approved promotion id is idempotent, while a different approval id for the same approved rule version is rejected so retained approval lineage cannot be overwritten. Dry-run previews return formula-broken rules as unmatched rule rows with critical validation issues, text predicates without comparison values as fail-closed validation issues, and top-priority ambiguity returns no selected rule or generated posting lines while retaining matched-row evidence and a critical priority-conflict issue for operator repair before promotion. Same-event rules with impossible effective windows are returned as unmatched rule rows with critical validation issues instead of being hidden by effective-date filtering.

The browser Manual Journal Entry workbench consumes the same evidence and lifecycle endpoints for controller actions. Source-evidence attachment posts the retained draft version, typed attachment metadata, optional line scope, actor, correlation id, and evidence links to `/api/ledger/journal-entry-workbench/evidence`, then refreshes the draft from the returned service-owned state. Submitted entries can be approved or rejected, approved entries can be posted, posted entries can generate separate reversal or rebook drafts, and posted entries can then be close-locked after close evidence is retained. Evidence can be attached through the shared evidence endpoint only while the entry is still mutable; posted, reversed, rebooked, and close-locked entries stay immutable. Direct reversal/rebook is available only from `Posted`; once an entry is `CloseLocked`, post-close corrections move through late-adjustment or restatement workflows rather than direct JE correction drafts. When close management marks a period locked, mutation requests fail before changing the draft, but validation can still surface the locked-period issue for operators. The browser renders returned transition audit rows with transition ids, correlation ids, evidence counts, and retained evidence routes beside typed correction links and generated correction drafts, but it does not mutate posted entries locally. It also displays a lifecycle checklist for draft version, validation, evidence, submission, approval, posting, reversal, rebook, close-lock, and transition audit readiness so each lifecycle gate is visible before the operator invokes a server-owned action.

The Accounting route also renders a close/report package cockpit backed by the shared close-management and accounting-report endpoints. It loads the close period plan, checklist dependencies, role-scoped sign-off requirements, close-calendar milestones, sign-off rows, materiality policy, period-lock posture, late adjustments, retained package history, financial statement package state, investor capital statement count, realized gain/loss, NAV, certification state, statement-line provenance, export-artifact certification state, restatement metadata, validation issues, and retained evidence counts from shared DTOs. It also surfaces certification safeguards for checklist sign-off, period-lock posture, critical validation blockers, export-artifact certification, restatement workflow state, and retained evidence package coverage before operators invoke certification. The close calendar is derived from the service-owned checklist state and carries milestone due date, owner, status, dependency count, required/approved sign-off counts, blocker reason, evidence links, and period-lock state so browser and WPF clients do not rebuild calendar posture locally. The browser can request a new accounting report package with workflow, fund, period, package-seed, and evidence context, request certification of a retained ready-for-review package with reviewer notes and evidence, request sign-off for the next ready checklist task with role, notes, correlation id, and retained evidence links, approve or reject retained late-adjustment requests with decision notes and evidence, and inspect the selected package's retained export-artifact manifest. Close transitions, dependency validation, materiality review validation, certification state mutation, statement artifact byte rendering, and restatement execution remain service-owned. Close task sign-offs require reviewer notes plus retained approval, sign-off, control, or review evidence that identifies the close task, workflow, or exact close period on the same artifact, retain the authenticated actor, reject sign-off while dependency tasks remain incomplete or the requested role is outside the task sign-off matrix, count only approved decisions toward the role-scoped approval cap, and promote the projected task to signed-off only when retained approvals satisfy the role-scoped task approval count. Late-adjustment rows show whether the retained request amount exceeds the retained materiality amount threshold and name the policy review role, but approval blockers remain service-owned. Late-adjustment requests require retained late-adjustment evidence that identifies the journal entry, workflow, or exact close period on the same artifact and are blocked once the close plan is period-locked by a retained close package; governed reopen or remediation must happen through Operations Continuity before new adjustments are accepted. Late-adjustment approval/rejection decisions require retained approval, rejection, decision, or review evidence that identifies the retained request, journal entry, workflow, or exact close period on the same artifact, retain the authenticated actor, and remove materiality pending-approval blockers once an approved or rejected decision is stored. Report package readiness requires retained ledger/trial-balance, reconciliation/tie-out, rendered report artifact, and NAV support evidence; missing families keep the package in Draft with critical validation issues. Close-backed report package readiness also requires the attached close workflow to be period-locked, even when checklist sign-offs and evidence families are otherwise complete. Report package output includes deterministic provenance rows for balance sheet, income statement, statement of changes in capital, investor capital, NAV, and restatement lineage, plus deterministic export artifact rows for financial statement PDF/workbook, investor capital statements, realized gain/loss CSV, NAV package, report-line provenance manifest, and restatement manifest when applicable. Each export artifact route resolves to a controlled JSON retrieval manifest with retained evidence, certification-state-bound content hash, package certification state, and `ExternalPostingAllowed = false`; the browser manifest inspection displays that metadata without enabling live posting, while downstream byte rendering of PDF/XLSX files remains separate from live GL posting. Final package certification additionally requires a retained approval, certification, sign-off, or review evidence artifact that itself references the retained package id, certification id, or exact package period, promotes export artifacts to `Certified`, promotes retained restatement workflow metadata to approved when present, recomputes retained content hashes from certified state and evidence, and rejects Draft, duplicate, critically blocked, period-unlocked, evidence-weak, split-evidence, or package/period-mismatched packages.

Late-adjustment request creation also fails closed unless one retained evidence artifact explicitly identifies both late-adjustment support and the journal entry, workflow, or close period; generic close support evidence and split support/provenance links are insufficient before storage or review.

Restatement requests stay governed report artifacts. A restatement reason creates submitted restatement workflow metadata, but package certification remains Draft unless the request identifies a retained certified prior package for the same fund and carries retained restatement or prior-package evidence links.

The Accounting route also surfaces external GL provider import posture and mapping profiles next to the imported provider evidence and reconciliation rows. Operators can compare QuickBooks, Xero, NetSuite, or fixture provider catalog rows for read-only import capabilities, credential state, retained mapping-profile coverage, and live-posting-disabled posture before preparing an export package. Operators can inspect certified account/dimension mapping coverage, create a guarded external GL export package from the latest reconciliation through `/api/accounting-system/export-packages`, retrieve its controlled manifest through `/api/accounting-system/export-packages/{exportPackageId}/manifest`, and certify the retained ready-for-review artifact through `/api/accounting-system/export-packages/certification`; the browser includes mapping, reconciliation, period, fund, package, generated export-line, manifest hash, and evidence context, while export-package state mutation and any future live posting remain service-owned and disabled by policy. The browser renders export safeguards for balanced reconciliation, certified mapping coverage, critical package validation blockers, controlled manifest hash and generated-line retention, and the live-posting-disabled gate so operators see the same certification blockers before export certification. Certified mapping profiles require a retained mapping approval, certification, sign-off, or review evidence artifact that itself identifies the retained mapping profile or provider/fund scope; a certified-looking profile without evidence, with only generic support evidence, with split support/approval evidence, or with wrong-profile approval evidence is downgraded to Draft before it can feed export certification or emit generated export lines. Export-package creation requires retained export package, approval, certification, sign-off, or review evidence that identifies the export ledger book plus the export fund, provider/fund scope, or exact export period before the artifact can reach ready-for-review state. Export certification requires a retained approval, certification, sign-off, or review evidence artifact that itself references the retained export package id, certification id, export ledger book, and exact export period, a certified mapping profile scoped to the export ledger book with account mappings that cover every reconciled GL account in the export period, certified dimension mappings, fund/entity scope on both Meridian and external GL sides, generated mapped export lines sourced from Meridian-owned ledger totals, and retained package state that still has live external GL posting disabled with a non-empty disabled reason; sparse, uncertified, evidence-weak, split-evidence, evidence-missing, evidence-unscoped, wrong-book-mapping, ledger-empty, posting-enabled, posting-posture-missing, or package/period-mismatched certifications retain or reject certification with critical validation issues, and duplicate or critically blocked certifications are rejected.

Generated external GL export lines are suppressed unless all retained dimension mappings are certified and carry fund/entity scope on both the Meridian and external GL sides.

## Current Boundaries

Implemented in this slice:

- Additive shared contracts for accounting rule definitions, dry runs, generated postings, dimensions, manual journal lifecycle transitions, close/report/export/reporting productization DTOs.
- Rule dry-run, persisted rule-test case, and rule-test suite services/routes over the existing accounting configuration store, including expected selected rule-version assertions, expected generated posting-line assertions, external GL dimension scope matching, static and formula-backed allocation weights, rounded residual handling, inherited rule/event/line/allocation dimensions, retained regression evidence links for saved test cases, service-owned rule version history, and fail-closed validation for generated posting references, duplicate active chart account paths, missing or duplicate generated posting line ids, missing or archived generated posting account references, missing or duplicate allocation ids, event-specific non-positive allocation weights, missing or duplicate condition ids, malformed amount-threshold predicates, inverted amount-between ranges, allocation formula references, and ambiguous top-priority dry-run matches.
- Activation readiness gates for promotion-gated posting rules, including approved rule/version/approval-specific promotion approval/certification/sign-off/review evidence that is invalidated after material rule edits unless a fresh approval id is supplied, passing evidence-backed saved regression tests for the current rule version, and critical blockers for same-priority rules with overlapping event, effective-date, and dimensional scope.
- Manual journal lifecycle service and route for validate, submit, attach evidence, approve, reject, post, close-lock, reverse-draft, and rebook-draft actions.
- Manual journal dimensional normalization that propagates fund, entity, sleeve, strategy, investor, capital-account, instrument, tax-lot, cost-center, counterparty, and external GL dimensions from header/rule context into saved JE lines.
