# Security Master Class-Plumbing Codegen (Prototype)

**Status:** draft
**Owner:** core-team
**Reviewed:** 2026-11-25
**Scope:** Engineering
**Roadmap:** `W11-PACK-002` (split from `W11-PACK-001` under `DEC-PACK-SPLIT-001`)

This plan records the prototype for item E2 of the Security Master architecture review of
2026-11-24, which challenged `W11-PACK-001`. The repository owner chose **prototype only**: the
generator and its equivalence test live in the test project, and the hand-written source stays the
source of truth. Switching `src/` to generated code is a separate decision that has not been made.

## Problem

Adding a Security Master class takes about 18–20 hand-edited source files. The edits include:

- the F# `SecurityKind` match sites: `AssetClassRegistry.keyOf`, the classification row,
  `SecurityKindPersistence` (two matches), `SecurityMasterLegacyUpgrade` and
  `Interop.SecurityMaster`;
- `SecurityMasterMapping.ToSecurityKind` and `SchemaBoundDecodeClasses`;
- pack-readiness rows, `ClassificationLabelReader.KnownCaseNames` and upcaster-chain entries;
- two classification tables, the F# `AssetClassRegistry` and the C# `SecurityAssetClassCatalog`,
  which are kept equal only by tests.

PR #3736 makes `FS0025` (incomplete match) a build error in
`src/Meridian.FSharp/Meridian.FSharp.fsproj`. That PR is an open draft as of 2026-11-25; on
`main` the warning is not yet an error. Once it merges, the compiler finds a missing F# arm. It
still will not find a missing C# arm, a missing row in a table or a missing string list entry.

| Item | Scope |
| --- | --- |
| `W11-PACK-002` | Generate the mechanical class plumbing from one declaration, built on `SecurityAssetTermsCodecBindings` and `SecurityAssetClassCatalog`. Compiled classes change through code review, not through runtime activation. |

## Prototype

| File | Role |
| --- | --- |
| `tests/Meridian.Tests/SecurityMaster/SecurityClassPlumbingDeclaration.cs` | One row per class, holding only what the catalog and the codec bindings do not already say: the structural classification, the terms type when it is not `{Name}Terms`, and the arms that are not mechanical (the `Bond` decode wrapper and the profile-backed `CustomAsset`). |
| `tests/Meridian.Tests/SecurityMaster/SecurityClassPlumbingGenerator.cs` | Emits seven sites from the declaration. Codec arm parameters come from the binding flags (`ReadsResolvedTerms`, `VersionedSchedules`, `WritesConventionsFlag`, `Inputs`), using the same rules as `SecurityFlatCodecGenerator`. Classification cases are resolved against the F# unions by reflection, so a label that names a nullary case renders as that case and any other label renders as `OtherFamily` or `OtherSubType`. |
| `tests/Meridian.Tests/SecurityMaster/SecurityClassPlumbingGenerationTests.cs` | Regenerates each site and requires the hand-written source to equal it. It also checks the declaration against the catalog and the compiled union, and shows that one new declaration row plus one binding adds an arm to every generated site. |

Unlike `SecurityFlatCodecGenerationTests`, there is no accept switch: the test only compares and
never writes to `src/`.

### Sites the generator covers

| Site | File | Comparison |
| --- | --- | --- |
| `SecurityKind` union cases | `src/Meridian.FSharp/Domain/SecurityMaster.fs` | Exact and ordered. Doc comments are ignored. |
| `AssetClassRegistry.keyOf` arms | same | Exact and ordered |
| `AssetClassRegistry` descriptor rows | same | Exact and ordered |
| Flat-writer dispatch arms (all classes except `CustomAsset`) | `src/Meridian.FSharp/Interop.SecurityMaster.fs` | Exact and ordered |
| `ToSecurityKind` decode arms | `src/Meridian.Application/SecurityMaster/SecurityMasterMapping.cs` | Exact text, compared as a set because the switch matches distinct string constants |
| `SecurityAssetClassNames` constants | `src/Meridian.Contracts/SecurityMaster/SecurityAssetClassCatalog.cs` | Exact and ordered |
| `SecurityAssetClassCatalog` row heads | same | Exact text, compared as a set (see findings) |

The decode method list (`GeneratedDecodeClasses`) and the codec arms themselves are already
generated by `SecurityFlatCodecGenerator`.

### Sites the generator does not cover

These sites state per-class meaning rather than plumbing, so a declaration row cannot derive them:

- `SecurityKindPersistence`: the two matches listing which members of each embedded module a flat
  row persists.
- `SecurityMasterLegacyUpgrade.termsFromKind` (economic term modules per class) and the
  `Deposit` and `OtherSecurity` sub-type refinements in `classificationFromKind`.
- The `Interop.SecurityMaster` rate-unit arms and the bespoke `CustomAsset` writer arm.
- `SchemaBoundDecodeClasses`. Its order records the migration cohorts, and a sweep test already
  holds it to the catalog as a set.
- `KnownCaseNames`. It lists the F# classification unions, not the classes, and a test pins it by
  reflection. It changes only when a new nullary family or sub-type case is added.
- The body of each catalog row (lot unit, cash-flow behavior, terms version, aliases, upcaster
  chain) and the pack-readiness rows. These are product facts that belong to the catalog and the
  pack registry.

## Findings

1. **The two classification tables are generable from one declaration.** All 32 F# descriptor
   rows and their `keyOf` arms match the generated text exactly. A switch could therefore remove
   one of the two classification tables or generate both.
2. **The catalog's row order differs from the F# union order.** `SecurityAssetClassCatalog` places
   `CustomAsset` after `OtherSecurity`. The union, the registry and `SecurityAssetClassNames` place
   it last. `SecurityAssetClassCatalog.AssetClasses` is public and ordered, so a switch must either
   keep both orders or decide which one is canonical. The prototype follows the union and compares
   catalog row heads as a set.
3. **Codec dispatch is fully derivable from the binding flags.** The derivation has two declared
   exceptions: `Bond` calls a hand-written `DecodeBond` wrapper, and `CustomAsset` has no binding.
4. **The covered sites are 7 of the roughly 18–20 edits.** The rest are semantic (see above).
   Generating the plumbing reduces the mechanical edits but does not make a new class a one-row
   change.

## Decision still open

The owner decides whether `W11-PACK-002` switches to generated code. If it does, the switch needs:

- generated files under the [generated output delivery](../generated-output-delivery.md) rules;
- an accept-and-compare test like `SecurityFlatCodecGenerationTests`, so stale output fails the
  test lane;
- a decision on the catalog's order (finding 2);
- for each residual site, either a generator or an entry in a list of deliberate semantic edits.

Until that decision is recorded, the hand-written source is the source of truth, and this test
fails when the declaration falls behind it.
